# ADR 0011: File and Document Storage

**Status:** Accepted

**Date:** 2026-08-17

## Decision

Files are held in object storage behind a `StorageProvider` interface, and are described by a `StoredFile` row that is the authoritative record of what an object is, who owns it and whether it may be read.

- **Bytes never pass through the API.** The client requests a short-lived upload URL, `PUT`s directly to storage, then confirms. Downloads are the reverse: the API authorises, then returns a short-lived signed URL. Large-file traffic stays off the request path, which matters more here than usual because the same endpoints are used over rural mobile connections.
- **Validation happens twice** — when the URL is issued and again on confirm, against the object storage actually holds. A presigned URL is a capability to write *anything*, so the content type and size a client declares up front prove nothing. Only the observed object is authoritative.
- **A file is not downloadable until a scan clears it.** `PENDING_UPLOAD → PENDING_SCAN → AVAILABLE`, with `INFECTED` and `REJECTED` as terminal failures. Scanning runs as a WP-04 job on the `documents` queue, so a backed-up queue delays access rather than leaking unscanned bytes. A database `CHECK` constraint enforces that `AVAILABLE` requires a recorded clean scan, so no application bug can produce a downloadable file that was never scanned.
- **Object keys are server-generated** (`purpose/yyyymm/uuid.ext`) and never exposed through the API. The client filename is stored for display only: it is untrusted input, and using it in a key would leak personal data into storage paths and access logs.
- **Downloads are authorised in the API and the bucket is never public.** Purposes carrying PII or financial record — `KYC_DOCUMENT`, `INVOICE_PDF` — write an audit row on every download URL issued, per the `AGENTS.md` requirement to log high-risk exports.
- **`INVOICE_PDF` cannot be client-uploaded.** It is generated by the platform (WP-15B); accepting an upload would let a farmer or distributor supply their own "invoice".

### Read access

Most permissive first: any holder of `files:read:any`; then the uploader; then a member of the file's organisation holding `files:read:own`. A file with no organisation — a farmer's own evidence — is readable only by its owner and by `files:read:any` holders.

### Provider selection

`STORAGE_PROVIDER` selects the implementation. Only `local` exists. It is a genuine filesystem provider that **mimics presigned-URL semantics** rather than taking a shortcut: it returns a URL pointing at this API's own `storage/local-object` endpoint carrying an HMAC-signed, time-limited token. The client flow is therefore byte-identical between local disk and a cloud bucket, so switching providers cannot change client behaviour, and CI exercises the real flow including signature and expiry rejection.

**A cloud provider is deliberately not written yet.** Which cloud is an open business decision (`docs/REMAINING_IMPLEMENTATION_PLAN.md` §9, decision 3), and an SDK for the wrong provider is dead weight. Adding one is a single file implementing `StorageProvider` plus a case in the `StorageModule` factory; nothing else in the module is provider-aware. The factory **throws** on an unrecognised value rather than falling back to local disk, because silently writing production uploads to a container filesystem would lose them on restart.

### Virus scanning

`VIRUS_SCANNER=mock` recognises the EICAR test string and passes everything else. **This is not virus scanning.** It exists so the quarantine path is genuinely exercised end to end without a ClamAV daemon in CI — a spec uploads EICAR and asserts the file becomes `INFECTED` and stays undownloadable. Like the storage factory, an unrecognised value throws rather than falling back, because a misconfigured scanner would mark malware clean.

A `SCAN_FAILED` verdict is **not** a decision: the handler throws, the file stays `PENDING_SCAN` and undownloadable, and BullMQ retries and eventually dead-letters it for an operator. Neither clearing nor condemning a file on a failed scan is acceptable.

## Consequences

- KYC documents, product images, delivery proof, return evidence, visit evidence and support attachments now have somewhere real to live. WP-10r, WP-12r, WP-13r, WP-05r and WP-15B are unblocked.
- Existing `KycDocument.storageKey` and `SupportTicketEvidence.storageKey` free-text columns remain for rows created in the metadata-only era; new uploads populate a `storedFileId` foreign key instead. Migrating the legacy rows needs the pilot data decision in WP-16.
- Scanning adds latency between confirm and availability. Clients must treat `PENDING_SCAN` as a normal state and poll or re-read rather than assuming a confirmed upload is immediately downloadable.
- Rejected uploads are deleted from storage immediately; the `StoredFile` row is retained as `REJECTED` so the attempt stays auditable.
- The local provider is **not** production storage: no replication, no lifecycle policy, no server-side encryption. The go-live checklist must confirm `STORAGE_PROVIDER` and `VIRUS_SCANNER` are both real.

## Retention

Documented in `docs/SECURITY_AND_COMPLIANCE.md`. In summary: KYC documents are retained while the organisation is active and for the statutory period after closure; delivery and return evidence for the dispute window plus one year; product images indefinitely while the product is listed. Deletion is a `DELETED` status plus removal of the object, never a hard row delete, so the audit trail survives.
