# Security and Compliance

## Agronomy Content Governance

Advisory authoring and review use separate permissions, self-approval is blocked, every lifecycle change is audited, and only approved versions are eligible for generation. Farmer endpoints enforce membership ownership and advisory consent in the service layer. Notifications contain only the approved localized content and an owner-checked advisory-event link. Crop-protection product recommendations remain disabled and out of the MVP.

## Secrets

Never commit real secrets, API keys, private certificates, production database URLs, production payment credentials, production Tally details or private farmer data.

## Authentication

Protected requests support JWT authentication in production mode and verified mock headers only for local development/tests. Mock requests must include `x-user-id`, `x-user-role` and `x-organisation-id`, and the backend verifies that those headers match an active user, active organisation and active membership. Public marketplace discovery endpoints are unauthenticated, read-only and limited to approved farmer-safe product data. Farmer profile, address, cart, checkout, own-order, mock payment, cancellation and return-request APIs require the `FARMER` role in addition to farmer-owned permissions.

Farmer self-registration uses separate `FARMER_REGISTRATION` OTP challenges so generic OTP login cannot silently create an account. OTPs are stored only as salted hashes with expiry and bounded attempts; request and verification endpoints are rate limited. Registration consumes a verified challenge once and atomically creates the farmer-owned records and active shared-context membership with append-only audit records. The farmer app stores access and refresh tokens only in platform secure storage; ordinary preferences contain locale only. `SMS_PROVIDER=mock` remains a development/sandbox boundary and may expose a clearly labelled transient `mockOtpCode`; no build using that provider is production-ready.

The business web portal sends mock-auth headers only from server-side code. Browser-rendered components must not expose mock user IDs, organisation IDs or role headers.

Delivery availability endpoints require dedicated own-profile permissions and revalidate the authenticated user, membership, delivery-partner role and active delivery-partner organisation context. Availability is scoped by `(userId, organisationId)`, defaults to offline, and every actual state change is audited as `DELIVERY_PARTNER_AVAILABILITY_UPDATED`. Assignment creation independently requires an online profile in an active delivery-partner context; a client-side toggle alone cannot make an offline partner eligible.

Package QR issuance is restricted to the seller organisation or manage-any operations users. Only a SHA-256 hash is persisted; raw package codes are neither returned by order reads nor written to audit values. Pickup verification checks assignment ownership before state or label details, is rate-limited, counts and audits invalid attempts, and does not replace farmer OTP proof of final delivery. Camera permission is requested only by the scanner screen; manual entry provides a non-camera fallback.

## Authorisation

Enforce permission-based access on the server. Permissions are assigned through role-permission mappings seeded into the database. Resource-level access checks protect organisation-owned reads where non-admin users may only access their active organisation context.

## Audit

Security-sensitive and business-critical actions must create append-only audit logs with actor, role, organisation, action, resource, previous value, new value, timestamp, request ID and reason where applicable.

Phase 1A audits user creation, user/profile/status updates, organisation creation, organisation updates, organisation approval/rejection, membership creation and membership status changes. Phase 1B adds audit records for company profile creation/update, distributor profile creation/update, KYC document submission, KYC document metadata updates, KYC resubmission and KYC review decisions. Phase 1C exposes onboarding audit entries in the business portal with server-side permission enforcement. Phase 2A adds audit records for brand creation/update/submission/review, master product creation/update/submission/review, variant metadata creation and product document metadata creation. Phase 2B adds audit records for warehouse changes, batch metadata/status changes and append-only inventory movement records. Phase 2C adds audit records for distributor offer create/update/submit/review decisions. Phase 2E adds audit records for distributor offer pause, reactivation and archive transitions. Phase 3A adds audit records for farmer profile changes, farmer address changes and cart mutations. Phase 3B adds audit records for checkout creation, child product order creation, order inventory reservation and cart checkout clearing. Phase 3C adds audit records for mock payment intent creation, checkout payment status changes and child order payment status changes. Phase 3D adds audit records for checkout cancellation, child order cancellation and inventory reservation release. Phase 4A adds audit records for distributor fulfilment order acceptance and rejection. Phase 4B adds audit records for ready-to-pack and packed order transitions. Phase 4C adds audit records for product invoice generation. Phase 4D adds audit records for ready-for-pickup order transitions and product dispatch creation. Phase 4E adds audit records for delivery assignment, partner acceptance/rejection, operations reassignment, out-for-delivery, delivered completion and failed OTP attempts. Marketplace discovery and inventory reports are read-only and create no audit records.

## Payments

Do not store raw card information. Use provider abstractions. Confirm payment state server-side through secure provider events.

Phase 3C farmer payment APIs remain mock-only and require `Idempotency-Key` headers for intent creation and confirmation. The WP-07 provider boundary verifies webhook HMAC signatures against raw request bytes before parsing, persists only verified deliveries, deduplicates provider event IDs, processes them asynchronously and requires an exact provider-reported integer-paise amount before capture settlement. Rejected signatures write a security audit containing the payload digest and request metadata without retaining attacker-controlled bodies. No card details or payment credentials are stored or logged. `PAYMENT_PROVIDER` remains restricted to `mock` until a reviewed gateway implementation and merchant sandbox are available; production secrets must come from secret management.

## Data

Use UTC timestamps. Use UUIDs for public identifiers. Avoid physical deletion for financial, invoice, settlement and audit records.

Farmer leads contain personal contact data. Creation is limited to authenticated promoter and sales-partner contexts, own reads and mutations repeat `promoterUserId` ownership checks, and operations-wide access requires separate any-scope permissions. The app shows an explicit collection-purpose notice. Phone numbers are normalized for duplicate-open-lead detection and are masked in audit snapshots; lead data must not be copied into notifications, exports or screenshots without a separately authorised workflow. Generic lead updates cannot manufacture a farmer account or set `CONVERTED`.

KYC document handling and product document handling are metadata-only through Phase 3D. Do not store real private documents, signed URL secrets or production storage keys in the repository, local seed data, documentation or screenshots. Real upload validation, file size/type restrictions and authorised document access must be implemented before production document storage is enabled.

Farmer support ticket reads remain scoped by `raisedByUserId`, and order-linked ticket creation revalidates farmer ownership of the referenced child product order. Farmer reopen uses the dedicated `support-tickets:reopen:own` permission and repeats ownership validation in the service before allowing only resolved or closed tickets to transition. The farmer app does not expose the metadata-only evidence endpoint; secure upload validation and authorised storage are still required before attachments are enabled.

Farmer notification lists are backend-scoped by authenticated `recipientUserId`; detail and mark-read repeat owner-or-manager checks, and mark-read is audited. Mock-payment outcome, seller-order fulfilment, farmer-raised support-ticket and return/refund in-app rows are created and audited inside the state-change transaction, resolve the recipient from the farmer profile, use the farmer's stored locale and contain identifiers/status snapshots rather than secrets. Payment amounts come from the backend payment intent as integer paise; provider secrets and failure internals are not copied into the notification. Shared support workflows check the ticket's immutable raiser role before producing farmer notifications, so business-user tickets are not silently routed into the farmer channel. Mobile related-resource links are allowlisted to product orders, support tickets and return requests, whose destination APIs independently enforce ownership. A payment notification's `ProductCheckout` reference and all other unknown resource types remain informational because a multi-seller checkout has no single safe child-order destination. A notification reference is never treated as authorisation.

Farmer return eligibility, creation, own-list and cancellation endpoints resolve the authenticated user's farmer profile and repeat child-order/request ownership checks in the service. Cancellation requires `returns:cancel:own`, a user-scoped idempotency key and a pre-pickup state. Shared return detail dynamically enforces farmer ownership, active seller-organisation scope, or any-return permission. Operational queue access is forcibly scoped to the active distributor organisation unless `returns:read:any` is present; mutations repeat seller scope checks in the service. Return evidence can attach only after the existing upload policy and virus-scan gate marks an uploader-owned `RETURN_EVIDENCE` file `AVAILABLE`. Attachment repeats farmer ownership or seller/any-manage scope, is retry-idempotent for the same file/return/uploader, writes `RETURN_EVIDENCE_ATTACHED` audit in the transaction and moves only the file's organisation scope to the return seller; the object key is never returned. Return-pickup assignment requires any-manage authority and validates an active, online partner in an active delivery organisation. Partner reads and transitions repeat assigned-user ownership checks in the service; collection atomically updates assignment, return and order histories and audit. The legacy operations pickup path is rejected once an assignment exists. Creation uses user-scoped idempotency and the database prevents duplicate child-order requests. Transitions and inspection commit history, audit and any inventory movements together in serializable transactions. Inspection accepts only original reservations belonging to the returned order line, requires exact returned-quantity allocation, and prevents restocking blocked or expired batches. Workflow-owned return inventory movement types cannot be submitted through the manual inventory-adjustment endpoint. Refund creation requires any-refund authority and derives farmer, payment, seller order and amount from the inspected return; clients cannot submit an amount. Farmer refund reads repeat `farmerUserId` ownership checks. Successful mock confirmation is idempotent and atomically appends immutable refund/reversal ledger entries plus order, return, refund-event and audit history. Real-provider confirmation must authenticate signed webhooks before replacing the explicitly mock-only endpoint.

Product-order dispute creation repeats child-order ownership for farmers or active seller-organisation scope for distributors, requires a user-scoped idempotency key, accepts only approved terminal order states and relies on a database partial unique index to prevent concurrent non-closed disputes. Farmer lists are forced to `farmerUserId`; seller lists cannot override their active organisation; platform-wide reads require `disputes:read:any`. Participant notes require read-party scope and a separate idempotency key. Support/operations investigation and finance resolution use distinct permissions, so an investigator cannot award money. Resolution caps the farmer award at backend `farmerPayablePaise`, restores the snapshotted order status, appends a dispute-linked adjustment ledger row when needed, emits a farmer notification and writes audit in the same serializable transaction. Raw payment/refund/commission rows are never rewritten to implement an award.

Refund creation and mock confirmation use distinct server permissions and mandatory idempotency keys. Farmer reads are user-owned; operations/finance reads require any-refund permission. Creation accepts no monetary amount and resolves the approved value, farmer, child order and successful payment on the server. Confirmation refuses non-mock provider modes, persists the original actor and validated outcome in an immutable processing event, and queues only that event ID. The worker re-derives amounts and provider references from PostgreSQL, calls the provider without holding a transaction, then row-locks the refund and commits terminal event, negative ledger movements, commission reversals, status histories and audit atomically. Stable job/event identities prevent duplicate or stale execution; retry exhaustion uses the audited dead-letter workflow. The portal labels the action as development-only and cannot trigger real money movement.

Farmer phone and WhatsApp support launchers accept only centrally supplied E.164 numbers. Source code contains no real or production-looking support contact. WhatsApp uses an HTTPS `wa.me` handoff with localized prefilled text; the farmer must still approve sending in the external app. Missing, malformed or unlaunchable configuration falls back to the authenticated support-ticket flow.

Inventory movement rows are append-only through the API. Stock adjustments require a reason and must pass backend permission checks and non-negative balance validation.

Distributor offer availability is derived on the backend from active, unexpired inventory batches and latest inventory movement balances. Frontend clients must not provide or override farmer-visible stock quantities.

Marketplace discovery responses must not expose review-only metadata, private KYC data, private product document storage keys, raw file names, unapproved products, unapproved brands, unapproved offers, inactive warehouses, inactive distributor organisations or zero-stock offers. Seller and fulfilment visibility is intentionally limited to product purchasing context: distributor legal/display name, GSTIN, warehouse location metadata, fulfilment mode and delivery SLA metadata.

Offer pause, reactivation and archive actions require authenticated protected API calls, resource-level offer write checks and an audit reason. Inventory ageing reports require inventory read permission and must apply distributor resource scope for own-organisation users.

Farmer cart APIs store backend-generated price and availability snapshots but do not reserve inventory or create checkout/payment state. Cart subtotal values are backend-calculated from integer paise snapshots. Clients must not submit cart prices, subtotals or availability counts.

Kisan Club benefit administration requires the existing operations programme-management permission and records actor, role, request ID, before/after values and reason in audit. Clients never submit a binding benefit, farmer payable or subsidy amount. Cart estimates are display-only; serializable checkout re-evaluates membership, product programme, rule scope, live price and usage limits, then writes redemption and order totals atomically. Payment and refund services consume those persisted totals. Benefit funding and reversal use append-only ledger entries, and redeemed financial terms cannot be edited.

Kisan Club fulfilment list/detail/mutation services enforce resource ownership even when a route supports own-or-any permission alternatives. A promoter UUID from the client never grants access. Reassignment and cancellation require manage-any authority and an audit reason. Promoter coordination statuses are not accepted as delivery proof and cannot trigger product-order delivery, inventory movement, payment state, commission or payout. OTP delivery remains restricted to the existing authorised delivery assignment.

Delivery location is collected only in the foreground when an assigned delivery partner confirms farmer-OTP completion. The app explains the purpose before the operating-system permission prompt. Permission denial or unavailable location is stored as an outcome and does not block delivery; continuous or background tracking is not used. Exact coordinates remain inside the permission-protected assignment resource and must not be exposed in general reporting or notification payloads.

General promoter farm surveys outside Kisan Club do not collect or accept latitude or longitude. The existing Kisan Club survey path may accept coordinates only when its explicit farmer precise-location consent is active. A future general-location feature requires its own approved consent record and client permission flow; attribution alone is not location consent.

Promoter visit location is separately opt-in for each submitted visit. The partner app requests foreground permission only after the promoter enables location on the visit form, performs a single capture, and never starts background tracking. Denied and unavailable outcomes do not block the visit. The backend rejects partial coordinates, validates capture proximity to the visit timestamp, stores the permission outcome, and excludes raw coordinates from audit JSON. Access remains promoter-user and organisation scoped; operations/admin access requires the explicit any-scope permission.

Kisan Club benefit tokens are bearer credentials. The API returns the complete token only at issuance and persists a random public lookup reference plus a salted SHA-256 hash, never the secret code. Issuance and redemption are rate-limited; redemption has a five-attempt ceiling, expiry and one-time atomic consumption. The active membership-promoter relationship is checked both before checkout and inside the serializable order transaction. Token quote amounts cannot bind price or benefit. Assisted checkout reuses normal backend offer, inventory, benefit, seller-order and audit controls, refuses to overwrite a farmer's non-empty cart, and requires the existing in-app payment flow.

Checkout APIs require an `Idempotency-Key` header and store idempotency records scoped to the authenticated farmer user. Checkout revalidates cart items against current backend offer, catalogue, serviceability and inventory data before writing parent checkout, child product orders and reservation movements in one database transaction. Reservation movements use `RESERVED_FOR_ORDER` and cannot be created through manual inventory adjustment APIs. Phase 3C mock payment APIs require idempotency keys, verify checkout ownership through the farmer profile, write payment events and audit status transitions. Phase 3D cancellation APIs require idempotency keys, verify checkout/order ownership through the farmer profile, reject paid or payment-processing records, and release reservations only through append-only `RELEASED_FROM_ORDER` inventory movements. Phase 4A through 4E fulfilment APIs verify seller-organisation access for distributor users where distributor fulfilment permissions apply, permit status transitions only in the approved sequence, create invoices only for packed child product orders, create dispatch readiness only after invoice generation, create delivery assignments only after dispatch readiness, and do not release inventory or initiate refunds. WP-15A additionally blocks invoice generation unless seller GST identity/state, place of supply and checkout-time HSN/rate snapshots exist. Tax-inclusive breakup and seller/financial-year sequence allocation execute on the backend with integer paise inside the same serializable transaction as the immutable invoice; database constraints independently enforce component and header reconciliation. GSTIN edits clear verification and require a new organisation review. Invoice generation audits `PRODUCT_INVOICE_GENERATED`. Phase 4D dispatch readiness audits `PRODUCT_ORDER_READY_FOR_PICKUP` and `PRODUCT_DISPATCH_CREATED`. Phase 4E delivery completion verifies OTP and location-proof consistency on the backend, stores only OTP hash/salt/expiry/attempt metadata, records a denied/unavailable location outcome without coercing permission, includes the proof metadata in append-only audit snapshots, and does not persist photo evidence until authorised private file storage exists.

## Stored Files

Files live in object storage behind a `StorageProvider`; a `StoredFile` row is the authoritative record of ownership and readability. See `docs/DECISIONS/0011-file-and-document-storage.md`.

- **The bucket is never public.** Every download is authorised by the API, which then issues a short-lived signed URL. Object keys are server-generated and never exposed.
- **Nothing is readable until scanned.** A file is `PENDING_SCAN` and undownloadable until a scan records a clean result; a database `CHECK` constraint enforces that `AVAILABLE` requires one. A failed scan leaves the file unreadable and retries — it never defaults to clean.
- **Uploads are validated twice**, at URL issue and again against the object actually stored, because a presigned URL can be used to write anything.
- **KYC documents and invoices contain PII or financial record.** Every download URL issued for them writes an audit row naming the actor.

### Retention

| Purpose                                                 | Retention                                                                  |
| ------------------------------------------------------- | -------------------------------------------------------------------------- |
| `KYC_DOCUMENT`                                          | While the organisation is active, plus the statutory period after closure. |
| `INVOICE_PDF`                                           | Per the statutory record-keeping period for tax invoices.                  |
| `DELIVERY_PROOF`, `RETURN_EVIDENCE`, `SERVICE_EVIDENCE` | Dispute window plus one year.                                              |
| `SUPPORT_EVIDENCE`, `VISIT_EVIDENCE`                    | Two years from creation.                                                   |
| `PRODUCT_IMAGE`, `PRODUCT_DOCUMENT`                     | While the product is listed.                                               |

Deletion sets `DELETED` and removes the object; the row is never hard-deleted, so the audit trail survives. **The exact statutory periods need legal confirmation before pilot** — the table above is an engineering default, not advice.

Farmer data export and deletion requests under the DPDP Act 2023 must include stored files owned by that farmer.

## Development Providers

SMS, WhatsApp, email, payment and Tally providers must remain mock or sandbox until production readiness is approved.

`STORAGE_PROVIDER=local` writes to the container filesystem and has no replication, lifecycle policy or server-side encryption. `VIRUS_SCANNER=mock` only recognises the EICAR test string — **it is not virus scanning.** Both must be real before any environment holds real uploads, and both are on the go-live checklist.
